# PR #9 — Access login loop: root cause and evidence

## Confirmed root cause
`sync/access-verify.js` fetched Access JWKS with `{redirect:'error'}`. The deployed Cloudflare Workers runtime rejects that Fetch option with TypeError before sending the request. `deploy/v2.4/entry.js` catches the exception and returns HTTP 401 JSON. The frontend interprets 401 as a missing/invalid session and displays verification again. The real OTP session itself was valid.

The previous Base64URL normalization was NOT the root fix; requests after that change still returned TypeError. No UI or Access policy change can fix the unsupported Fetch option.

## Runtime reproduction — real workerd
Installed official workerd 2026-11-24 in temporary test storage. Compatibility date 2026-11-21 matches Preview. A synthetic signed RS256 Access JWT is processed by the actual verifier; a separate in-memory workerd service supplies JWKS, no database or external identity service.

Before fix, verifier returns:
`TypeError: Invalid redirect value, must be one of "follow" or "manual" ("error" won't be implemented since it does not make sense at the edge; use "manual" and check the response status code).`
Stack points to verifyAccess at JWKS fetch. This exactly reproduces the observed TypeError rather than guessing from a generic 401.

After changing only redirect:'error' → redirect:'manual': HTTP 200 and verified fixture identity. A redirecting JWKS endpoint is still rejected (response.ok=false); no redirect is followed and signature verification is not weakened.

Run: `TG_WORKERD_PATH=/path/to/official/workerd node sync/tests/access-workerd.cjs`.
