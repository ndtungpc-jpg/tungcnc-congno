# Preview initial Cloud ledger upload, checkpointed

Scope: only first initialization of the verified empty v24 Preview namespace. The owner accepted Gmail login and Devices & Sync UI on S24 before this task; those flows are unchanged. Ordinary nonempty-ledger reconciliation and the v2.3 engine remain intact.

## Implementation

1. Existing review/backup/readback/confirmation screen retains its layout. For a fully verified empty ledger, the action reads **Khởi tạo sổ Cloud từ thiết bị này** and uses the new initial-upload client rather than ordinary reconciliation.
2. Build an immutable, validated accounting snapshot using existing `initialSnapshot`; local recovery history and original revision remain on the device. Capture source and existing pending-queue fingerprints. Exported independent backup continues to include the complete original local ledger, Cloud snapshot and pending queue.
3. Send bounded text parts (80,000 UTF-16 code units, never splitting a surrogate pair; each server part <=400,000 UTF-8 bytes, all requests below the existing API request limit). This preserves JSON numbers, order-item arrays and multi-order payment groups exactly, without publishing incomplete records.
4. A single staging job binds the approved device, session ID, ordered part hashes, total snapshot hash, size, expected record/item/size counts, exact summary amounts and verified-backup hash. Each part insertion and next-index checkpoint update are one transaction. Retried identical requests are acknowledgments; changed content is rejected. Parts are retained for safe retries.
5. Finalize only after all parts and hashes match. Validate the complete schema, financial relationships and allocation groups; compare expected counts/items/sizes/debt. Enforce existing safe D1 row limits. Publish `sync_state`, one existing `initial-snapshot` receipt, and completion state in a single D1 batch transaction.
6. Existing devices read an empty ledger until publication, then one complete existing-format initial-snapshot receipt. Ordinary pushes are blocked while the job is uploading, including an SQL CAS guard against the begin/push race. A changed/nonempty ledger cannot be initialized or overwritten.
7. After finish (including a lost final ACK), verify remote snapshot hash, every record field through the full snapshot digest, item/size counts, summary and versions. Acknowledge only sync metadata with CAS. **No write of local `main`, including revision/recovery** occurs during initialization. Clear only the captured, unchanged pending queue whose full contents were already included in the verified snapshot. Local or pending-queue edits stop the flow without discarding new transactions.
8. Network interruption, closing/reopening the app and Pause retain checkpoints. Resume rebuilds the plan from the same unchanged local source and uses the same session. Source changes require explicit further reconciliation; the initializer does not guess a new source or reset staging data.

Access assertion verification, device signatures/nonces, revocation enforcement and owner-email restriction precede all new endpoints. No new authentication method, Worker, Production route or IndexedDB schema is introduced. The obsolete single-request bootstrap remains disabled.
